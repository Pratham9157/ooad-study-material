System Sequence Diagrams

⏱ 4 min read📚 Syllabus: Unit 4 · Unit 5

A system sequence diagram (SSD) shows, for one scenario of a use case, the events that actors send into the system and what comes back — treating the whole system as a single black box. It's the bridge between use cases (text) and design (objects).

The Problem: From Story to Software Operations

The Issue Book use case is a story in English. But software doesn't run stories; it runs operations. Before designing objects, we need to know precisely: what requests arrive at the system, in what order, with what data? Those requests — the system events — are what our design must handle.

🧠 Real-World Analogy

Think of a vending machine from the customer's side. You don't care about its gears; you only see what you do — insert coin, press "B4" — and what comes out — snack, change. An SSD is exactly that customer's-eye view of the system: inputs in, outputs out, insides hidden.

Understanding SSDs

  • Shows one scenario (usually the main success scenario) of one use case.
  • Participants: the actor(s) and the system as one black-box lifeline (:System) — plus any external systems. No internal objects.
  • Arrows into the system = system events. Each one becomes a system operation the design must implement.
  • Dashed arrows back = returned information.

Example: SSD for Issue Book

        :Librarian                                   :LibrarySystem
            │                                              │
            │  startIssue()                                │
            │─────────────────────────────────────────────►│
            │  enterMember(memberId)                       │
            │─────────────────────────────────────────────►│
            │◄─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ member details ─ ─ ─│
   ┌────────┼──────────────────────────────────────────────┼───────┐
   │ loop   │ [more copies]                                │       │
   │        │  enterCopy(copyId)                           │       │
   │        │─────────────────────────────────────────────►│       │
   │        │◄─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ title, dueDate ─ ─│       │
   └────────┼──────────────────────────────────────────────┼───────┘
            │  endIssue()                                  │
            │─────────────────────────────────────────────►│
            │◄─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ issue slip ─│

Compare with the use case steps: "starts a new session" → startIssue(), "enters the member ID" → enterMember(memberId), "enters a copy ID" (repeated) → loop + enterCopy(copyId), "ends the session" → endIssue().

How to Draw an SSD (Step by Step)

  1. Draw the actor lifeline on the left and :System as one black box on the right.
  2. Read the use case's main success scenario.
  3. For each step where the actor asks the system to do something, draw an arrow to the system with an event name and parameters.
  4. Draw dashed return arrows for important information sent back.
  5. Use a loop frame for repeated steps.

Naming guideline: name events at the level of intent, not the input device — enterCopy(copyId) ✅, not scanBarcode() ❌; Larman's POS: enterItem(itemID, quantity), not scan(). Start names with a verb.

Relationship Between Sequence Diagrams and Use Cases (Syllabus Unit 4)

   Use case (text)  ──one scenario──►  SSD  ──system events──►  System operations  ──design──►  Sequence diagrams
   "UC1 Issue Book"                    (black box)                startIssue, enterMember,       (objects INSIDE the
                                                                  enterCopy, endIssue            system collaborate)
  1. A use case is text; an SSD is a picture of one of its scenarios.
  2. Each system event becomes a system operation — together they form the system's public interface.
  3. (Optionally) each operation gets an operation contract describing the state changes (e.g. enterCopy: "a Loan was created and linked to the Member and BookCopy; the copy's status became issued").
  4. In design, each system operation is designed as a design sequence diagram (next lesson) showing which objects collaborate to handle it — starting from a controller object (GRASP Controller, Lesson 13.3).

🔑 Key Takeaways
  • SSD = one use case scenario; actors + the system as a single black box; system events in, results out.
  • Each system event → a system operation the design must handle.
  • Use case → SSD → system operations → (contracts) → design sequence diagrams.
  • Name events by intent (enterItem), not hardware actions (scan).
⚠️ Common Mistakes Students Make
  • Drawing internal objects (:Member, :Loan) in an SSD.
  • Naming events after UI actions ("clickOK").
  • Cramming every alternative scenario into one SSD.
📝 How This Is Asked in Exams
  • "What is an SSD? Draw the SSD for <use case>."
  • "Explain the relationship between use cases and sequence diagrams." → the flow above + comparison table.
📘 Exam-Ready Definition

A system sequence diagram (SSD) is a picture that shows, for one particular scenario of a use case, the events that external actors generate, their order, and inter-system events, with the system treated as a black box. Each incoming system event corresponds to a system operation that the system must be designed to handle.

Quick Check

Q1 · Draw the system events for an ATM "Withdraw Cash" main scenario.
Show Answer

insertCard(cardNo) → enterPIN(pin) → withdraw(amount); returns: PIN request, menu, then cash + card + receipt. (The Bank System may appear as an external lifeline with verify / authorize messages.)

Q2 · Why is scanBarcode() a poor SSD event name?
Show Answer

It describes the input device rather than the intent; if the library switches to RFID or typing, the requirement hasn't changed. enterCopy(copyId) captures the intent.
